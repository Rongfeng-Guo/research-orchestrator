# 项目总览

## 1. 这个项目在做什么

DeepResearch Agent 想解决的不是普通问答，而是“复杂研究任务自动化”。

这里的复杂研究任务通常有几个特点：

- 用户问题很宽，不是一跳能答完
- 需要多次检索和交叉验证
- 需要把结果组织成结构化报告，而不是一段随手回答
- 希望系统能够记录中间结论、处理上下文膨胀、在必要时修复错误

所以，这个项目把“研究”拆成了一条流水线：

1. 规划：把大问题拆成多个可执行子问题
2. 调度：按依赖关系并发执行子问题
3. 执行：调用工具做搜索、浏览、论文查询、计算
4. 记忆：把子结果存起来，供后续任务复用
5. 合成：把多个子结果整理成最终报告
6. 修复：如果报告质量不够，进入 Red/Blue 对抗修复
7. 评测：用规则指标、Judge、消融实验和 benchmark 评估效果

在当前代码里，这条流水线又多了一层 evidence-aware control：

- 共享记忆不仅保存结果，还能产出 `EvidenceSnapshot`
- `Orchestrator` 会把 `recommended_action`、`covered_terms`、`missing_terms` 等策略信号写入上下文
- 这让系统从“固定执行 DAG”往“根据证据状态调整下一步行为”更近了一步

## 2. 它不是什么

为了避免误解，先说明它不是什么：

- 它不是一个简单的“把 query 直接发给 LLM”脚本
- 它不是一个已经完全产品化的商业级 deep research 服务
- 它不是严格意义上拥有多个高度异构角色的 agent 平台

在当前实现里，`search`、`analyze`、`verify` 三类任务最终都由 `ResearcherAgent` 完成，只有最后的报告合成才切换到 `SummarizerAgent`。这意味着它更像“一个编排器 + 一类通用研究 worker + 一个合成器”，而不是很多职责完全不同的 agent 各司其职。

## 3. 核心价值主张

相较于单轮问答，这个项目主要想证明三件事：

1. 复杂问题可以先拆解，再回答。
2. 长过程研究里需要记忆、压缩和失败恢复。
3. 报告质量可以通过对抗修复和评测体系显式提升和衡量。

从代码角度看，项目最大的价值不在某个单一模型，而在于这条完整链路：

- `Planner` 负责把问题变成 DAG
- `Orchestrator` 负责状态机和并发调度
- `ResearcherAgent` 负责工具调用式研究
- `SummarizerAgent` 负责最终写报告
- `SharedMemoryStore` 负责跨任务记忆
- `EvidenceAwareResearchPolicy` 负责把记忆整理成可执行的研究策略信号
- `ContextCompressor` 负责上下文控制
- `AdversarialLoop` 负责报告修复
- `evaluation/` 负责实验和量化评估

## 4. 输入和输出长什么样

### 输入

最典型的输入是一个自然语言研究问题，例如：

- “2024-2025 年大模型 Agent 技术趋势与落地案例研究”
- “比较 GPT-4o、Claude 3.5 Sonnet、DeepSeek-V3 的推理能力差异”
- “分析中国新能源车渗透率提升对燃油车产业链的冲击”

### 输出

系统最终返回一份 Markdown 报告，内容包括：

- 报告正文
- 元信息
- 置信度
- 搜索轮数
- 重规划次数
- 对抗轮数
- 来源链接列表

这在 `src/core/runner.py` 的 `_format_report()` 里实现。

## 5. 六大模块的“设计目标”和“当前状态”

| 模块 | 设计目标 | 当前状态 |
| --- | --- | --- |
| M1 Orchestrator | 状态机驱动的多任务编排与调度 | 已实现，是系统中枢 |
| M2 Planner | 用 LLM 把问题拆成 DAG | 已实现，支持 replan |
| M3 Compressor | 控制长上下文膨胀 | 已实现，但目前主要用于记忆上下文压缩 |
| M4 Memory Store | 跨任务共享记忆与语义检索 | 已实现，包含去重与冲突检测 |
| M5 Adversarial Loop | Red/Blue 报告修复 | 已实现，但只在报告置信度不高时触发 |
| M6 Evolution Engine | 在线自进化 / 训练闭环 | 仍属原型接口，训练部分是 placeholder |

## 6. 当前实现最重要的几个事实

### 事实 1：它的“多智能体”更偏编排，而不是很多不同人格 agent

当前系统里的差异化主要体现在：

- 任务被拆成多个子任务
- 子任务可以并发执行
- 不同阶段可使用不同模型后端

但在 agent 实现层，`search`、`analyze`、`verify` 没有被拆成三套完全不同的行为逻辑。

### 事实 2：研究 worker 的工具调用是受强约束的

`ResearcherAgent` 的 prompt 明确限制：

- 最多两次工具调用
- 两次之后必须总结

所以它不是“无限浏览直到彻底查清”的代理，而是一个偏保守、偏实验型的 tool-calling worker。

### 事实 3：对抗修复不是默认无条件执行

虽然配置里 `adversarial.enabled` 默认是 `true`，但 `Orchestrator` 会先看合成报告的 `confidence`。如果报告置信度已经达到 0.8 以上，就直接跳过 Red/Blue 环节。

这意味着：

- 对抗模块更像“有条件的质量增强器”
- 它不会在每次运行中都参与

### 事实 4：项目重视“实验可解释性”

这个仓库不只是跑单次 query，还包含：

- 标准评测入口
- 模块消融
- 对抗轮数消融
- Agent vs 单轮 LLM benchmark
- 汇总报告生成

这说明它的目标不仅是“做出来”，还是“能量化地说明哪些模块有价值”。

## 7. 你应该如何理解它的成熟度

比较准确的定位是：

> 一个结构完整、可运行、可实验、适合继续扩展的深度研究 Agent 原型系统。

它已经具备：

- 清晰的模块边界
- 配置化的后端路由
- 工具层
- 记忆层
- 报告合成
- 批量实验

但它还保留明显的原型痕迹：

- 某些行为仍 heavily 依赖 prompt
- 自进化训练还没真正闭环
- 工具层和配置层有少量不一致
- 若用于生产，还需要更严格的安全、缓存、可观测性和容错设计

## 8. 如果只记住一件事

如果只用一句话概括这个项目：

> 它是在用“规划 + 并发子任务 + 工具调用 + 共享记忆 + 报告合成 + 对抗修复 + 评测”的方式，把复杂问题转成一份更像研究报告的输出。
