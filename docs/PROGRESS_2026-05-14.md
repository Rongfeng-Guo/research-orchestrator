## 2. 今天最新完成的内容

本轮最新进展，不是继续补离线训练，而是补上了 `search policy` 的运行时接入。

### 2.1 新增 runtime search policy 封装

新增文件：

- `src/search_policy/runtime_policy.py`

新增能力：

- 复用 `src/search_policy/train_policy.py` 训练出的 JSON 模型；
- 在运行时根据当前搜索状态输出：
  - `search`
  - `browser`
  - `stop`
- 同时返回：
  - `confidence`
  - `probabilities`
  - `guidance`
  - `browser_url`
  - `can_continue`
  - `enforce_stop`

这一步的意义是：

- 把离线 trainer 的产物真正变成运行时可消费的 policy；
- 不需要先接重型 online RL，也能做 learned vs heuristic 的在线对照。

### 2.2 SearchPolicyDatasetBuilder 暴露运行时状态接口

涉及文件：

- `src/search_policy/dataset.py`

新增/调整：

- `new_state()`
- `features_from_state()`
- `observe_action()`

同时补充了运行时状态字段：

- `last_tool_name`
- `last_query_text`
- `last_top_urls`

意义：

- 离线训练与在线推理共用同一套特征定义；
- 避免训练时和运行时使用两套不一致的 feature engineering。

### 2.3 Search policy 已接入模块初始化链路

涉及文件：

- `src/core/runner.py`
- `src/orchestrator/agent_pool.py`
- `configs/default.yaml`

当前行为：

- 新增 `search_policy` 配置段；
- 默认 `mode: off`、`enabled: false`，保持主链安全；
- 若启用：
  - 显式区分 `off / heuristic / learned`；
  - `heuristic` 模式不会加载本地 learned model；
  - `learned` 模式默认从 `artifacts/search_policy.json` 加载模型；
  - 模型不存在但允许回退时，使用 heuristic fallback；
  - 初始化失败时只记录 warning，不阻断主流程。

这意味着：

- runtime policy 已不是手工注入，而是正式进入配置驱动链路；
- 后续做 smoke run 或对照实验时，不需要再改源码。

### 2.4 Search policy 已接入 ResearcherAgent 的 turn loop

涉及文件：

- `src/agents/researcher.py`

已接入的两个关键节点：

1. 当模型没有调用工具、试图直接结束时：
   - runtime policy 会基于当前状态给出 `policy_advice`；
   - 若建议继续搜索，则向模型追加明确 guidance，强制再走一轮工具决策。

2. 当工具调用完成后：
   - runtime policy 会再次判断下一步更适合：
     - 继续 `search`
     - 进入 `browser`
     - `stop`
   - 若高置信度建议停止，会触发 `learned_policy_stop`。

同时，结构化动作日志里现在会新增：

- `action_type = policy_advice`
- `policy_stage = assistant_no_tool | post_tool`
- `recommended_action`
- `policy_source`
- `probabilities`
- `feature_vector`

意义：

- learned policy 不再只是线下指标，而是真的影响在线执行；
- 后续可以直接分析“policy 介入后到底改变了哪些工具调用行为”。

## 7. 建议的下一步

如果继续推进，最合理的顺序是：

1. 扩大 `search_cache` 规模，而不是只用 3 条 query：
   - 优先补足 `browser` 类别；
   - 让 learned policy 不再严重受标签偏斜影响。
2. 把当前对照从 2 题 smoke 扩展到更稳定的 mini-benchmark：
   - 固定题集
   - 固定顺序
   - 输出统一对比表
3. 针对这次暴露的问题做 reward / stopping 调整：
   - 先确认 browser 类缺失是数据问题还是 reward 问题；
   - 不要在没补数据前同时改 reward、route、rewrite。
4. 再考虑把动作空间继续扩展到：
   - route selection
   - query rewrite
   - online RL / GRPO

如果只选一个下一步，我建议：

> **先扩充 `search_cache`，优先补足 browser 类样本；然后在完全相同配置下重训并复跑修复后的 head-to-head，确认 learned 现在学到的到底是“更好的浏览策略”还是“更多的搜索循环”。**
