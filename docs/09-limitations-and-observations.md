# 局限、实现差异与阅读时的注意点

这篇文档专门记录 README 的愿景和当前代码现实之间的差异，以及一些读源码时很容易忽略的事实。

## 1. 这是研究原型，不是成熟产品

从整体结构看，这个项目已经相当完整。

但它依然更接近：

- 可运行研究原型
- 演示系统
- 架构探索项目

而不是：

- 面向真实复杂网页环境的生产代理
- 经过充分鲁棒性验证的在线服务

## 2. 多智能体是有，但没有想象中那么重

项目确实有：

- Planner
- Researcher
- Summarizer
- Red
- Blue

但要注意：

- `search`
- `analyze`
- `verify`

三类子任务在执行层都复用 `ResearcherAgent`。

## 3. 工具调用深度有限

`ResearcherAgent` 的 prompt 明确限制：

- 每个子任务最多 2 次工具调用

这带来的后果是：

- 子任务执行成本可控
- 行为更稳定
- 但深挖能力有限

## 4. Browser 不是通用网页浏览器

当前 `browser` 只是：

- HTTP 抓取
- HTML 提取正文

它不擅长：

- JS 重渲染页面
- 复杂登录态页面
- 动态内容交互

## 5. Code Sandbox 仍然很受限

名字叫 `code_sandbox`，但当前实现并不是完整沙箱。

它的特点是：

- 默认禁止 import
- 不适合复杂脚本执行
- 更适合小规模表达式或非常简单的 Python 逻辑

## 6. 记忆层的语义能力是启发式

`SharedMemoryStore` 做了很多工作：

- embedding 检索
- 去重
- 矛盾检测

但要注意：

- 去重依赖相似度阈值
- 冲突依赖否定词和反义词启发式

## 7. 压缩层的接入范围还有限

压缩模块本身设计得比它在主流程中的使用更充分。

现实情况是：

- 有 L1/L2/L3 三层策略
- 但当前主流程中主要用于规划前的记忆上下文压缩

## 8. 对抗层是文本修复，不是严格验证

Red/Blue 环能带来质量提升，但它不是形式化验证系统。

本质上仍然是：

- 用 LLM 挑错
- 再用 LLM 重写

## 9. Evolution 模块目前是最明显的占位区

虽然：

- 配置项很多
- 目录结构也有
- 训练循环骨架也有

但训练接入部分有明确 placeholder 和伪代码。

因此不要把它当作已经接好的在线强化学习系统。

## 10. 注释、README 与代码之间存在个别差异

### 例子 1：ResearchBench 数量描述

- 文件注释说 20 道题
- 实际默认题量是 35

### 例子 2：Evolution 的存在感

- README 中把自进化列为六大模块之一
- 当前主线运行中它更多还是关闭状态和预留接口

### 例子 3：对抗阈值的理解

- 配置里有对抗内部的 `score_threshold`
- 但主流程是否进入对抗，还要先过“报告 confidence < 0.8”的外部门槛

## 11. 当前最值得继续增强的方向

- 更深的工具调用循环
- 更真实的浏览能力
- 更强的工具选择策略
- 更严格的引用与事实核验
- 更深度接入压缩与记忆
- 把 evolution 真正接成闭环
