# DeepResearch Agent 继续推进记录

日期：2026-05-25

本轮工作的目标很窄：

> 不再继续猜测 guardrails 会不会改善 no-leak heldout，而是把真实搜索环境修正回来，按与 2026-05-23 相同的 8-query cross-fold live protocol 重跑一次，然后直接看 learned vs heuristic 的结论有没有变化。

结论先写在前面：

- 环境侧确实修掉了一个关键偏差：之前的 rerun 默认落到 `serpapi`，因为缺少 `SERPAPI_KEY` 被自动切成 `mock_mode=True`，那轮结果不能作为正式科研更新；
- 本轮把本地后端固定到 `bing_html` 后，真实 live rerun 已经跑完；
- 但结果**没有**支持 “guardrails 让 learned 变稳” 这个判断；
- 相反，在本轮 `bing_html` rerun 上，**heuristic 同时更高分且更便宜**；
- 更关键的是，`guardrail_trigger_count = 0`，说明这轮 live rerun 中 guardrails 实际上没有触发，不能把结果变化归因于 guardrail 生效。

## 1. 先修环境偏差：把默认真实搜索后端从隐式 `serpapi` 改成 `bing_html`

这轮首先确认了一个之前没有写清楚、但会直接污染 rerun 解释的环境问题。

当前：

- `configs/real_evidence_fast_seeded_browser.yaml` 里
  - `tools.web_search.mock_mode: false`
- 但 `src/core/runner.py`
  - 若 `SEARCH_BACKEND` 未设置，会默认取 `serpapi`
  - 且若缺少对应 key，就会自动切到 `mock_mode=True`

而本机 `.env.local` 之前只有 LLM 相关配置，没有显式：

- `SEARCH_BACKEND`

这导致我上一轮 guardrails rerun 虽然命令行看起来是在跑 live evaluation，实际上日志里已经明确写了：

- 搜索后端 `serpapi` 缺少 `SERPAPI_KEY`
- 自动切换为 `mock_mode=True`

因此那轮结果只能当“代码链路验证”，不能和 2026-05-23 的真实网络基线直接比较。

本轮修正：

- `.env.local`
  - 新增 `SEARCH_BACKEND=bing_html`

修正后做了两个 smoke：

1. 直接实例化 `WebSearchTool`
   - `backend = bing_html`
   - `source = bing_html`
   - `error = None`
2. 通过 `runner.initialize_modules(...)`
   - `web_search_tool = WebSearchTool`
   - `backend = bing_html`

这说明后续 rerun 不再因为缺 key 自动退回 mock，而是确实走无 key 的真实 HTML 搜索路径。

## 3. 新结果：heuristic 现在是更好的模式

本轮聚合结果如下：

| mode | success | avg_composite | avg_citation | avg_tokens | avg_tool_calls |
|---|---:|---:|---:|---:|---:|
| heuristic | 8/8 | 0.576 | 0.284 | 9769.4 | 2.88 |
| learned | 8/8 | 0.564 | 0.278 | 15212.0 | 4.25 |

learned 相对 heuristic 的聚合差异为：

- `quality_delta = -0.012`
- `citation_delta = -0.005`
- `token_delta = +5442.6`
- `tool_delta = +1.38`
- `elapsed_delta = +5.63s`

这次已经不是 2026-05-23 那种：

- learned 略好且更省

而是反过来：

- heuristic 质量更高；
- heuristic token 更低；
- heuristic 工具调用更少；
- heuristic 耗时也更短。

所以如果只看这轮 rerun，最诚实的判断是：

> 在 `bing_html` 真实搜索后端下，当前 learned policy 并没有优于 heuristic，反而在 aggregate 上同时输掉了质量和成本。

## 4. 和 2026-05-23 基线相比，发生了什么变化

2026-05-23 的 live cross-fold 基线是：

| mode | avg_composite | avg_citation | avg_tokens | avg_tool_calls |
|---|---:|---:|---:|---:|
| heuristic | 0.557 | 0.294 | 29231.6 | 7.50 |
| learned | 0.563 | 0.294 | 20162.6 | 5.38 |

而本轮 `bing_html` rerun 变成：

| mode | avg_composite | avg_citation | avg_tokens | avg_tool_calls |
|---|---:|---:|---:|---:|
| heuristic | 0.576 | 0.284 | 9769.4 | 2.88 |
| learned | 0.564 | 0.278 | 15212.0 | 4.25 |

可以看到两个层面的变化：

1. **整体执行都变“更短、更便宜”了**
   - heuristic token 从 `29231.6` 降到 `9769.4`
   - learned token 从 `20162.6` 降到 `15212.0`
   - 两边 tool calls 都明显下降

2. **learned 的相对优势消失了**
   - 原来 `quality_delta = +0.005`
   - 现在 `quality_delta = -0.012`
   - 原来 `token_delta = -9069.0`
   - 现在 `token_delta = +5442.6`

也就是说，这轮不是“learned 仍然 mixed 但略正”，而是：

> 在当前 rerun 条件下，heuristic 成了新的 winner。

## 5. fold-level 结果：只有 fold 02 略微转正，但整体没有收敛成稳定胜利

本轮 fold-level delta：

| fold | heldout_ids | quality_delta | citation_delta | token_delta | interpretation |
|---|---|---:|---:|---:|---|
| fold_01 | `fast_ai_law_001`, `fast_law_ai_safety_001` | -0.021 | +0.007 | -113.5 | cost down, quality down |
| fold_02 | `fast_energy_001`, `fast_energy_h2_001` | +0.002 | +0.035 | +17850.0 | quality up, cost up |
| fold_03 | `fast_ai_code_001`, `fast_law_platform_001` | -0.014 | -0.086 | -39.0 | cost down, quality down |
| fold_04 | `fast_fin_reg_001`, `fast_energy_wind_001` | -0.014 | +0.022 | +4073.0 | mixed or unclear |

相对 2026-05-23 的关键变化：

- fold 02 从明显负例变成了轻微质量正例
- 但代价是：
  - token 大幅上升
  - 不再是“质量改善且更省”
- fold 03 从原先最强正例之一，转成了负例
- fold 04 也从原先“质量提升且成本大降”退化成了 mixed

因此这轮结果不能解释成：

- variance 被压住了

更像是：

- variance 结构换了位置；
- 但 learned 没有变成稳定更优。

## 6. 一个更关键的新发现：guardrails 没有触发

这轮本来最重要的验证目标，是检查：

- fold 01 的 premature stop 是否下降
- fold 02 的 over-search 是否下降

但聚合 summary 里出现了一个更值得先写下来的事实：

- `avg_guardrail_trigger_count = 0.0`
- `avg_policy_enforce_stop_count = 0.0`
- `avg_policy_advice_count = 0.0`

而且四个 folds 下 heuristic / learned 全部都是 `0.0`。

这意味着：

1. 本轮 guardrails 代码虽然在仓库里存在；
2. 相关测试也通过；
3. 但在这次 live rerun 里，**policy trace 没有记录出任何 guardrail 触发**；
4. 因此不能把 rerun 结果解释为“guardrails 生效后的 learned 表现”。

换句话说，当前更合理的判断不是：

- “guardrails 无效”

而是：

- “guardrails 在这轮 live protocol 中并没有实际介入，或者介入后没有被计入统计”。

这一步很重要，因为它直接决定下一步该修哪里：

- 现在不应先讨论 reward / threshold；
- 而应先查清楚 runtime policy advice / guardrail metadata 为什么全是零。

## 7. 当前最诚实的项目判断

截至 2026-05-25，这条主线的结论应更新为：

1. **Evidence-readiness claim 仍然成立**
   - 8-query benchmark 已通过 formal evidence gates
   - 这部分没有被本轮推翻

2. **Learned-policy superiority claim 进一步变弱**
   - 2026-05-23 时还是 “aggregate 略正但 fold-level mixed”
   - 2026-05-25 这轮 `bing_html` rerun 则变成 “aggregate 负向，heuristic 更强”

3. **Guardrail hypothesis 目前尚未真正被评到**
   - 因为 live rerun 里 `guardrail_trigger_count = 0`
   - 所以现在还不能判断 guardrails 是否改善了 premature stop / repetitive continue

因此当前论文叙事应进一步收紧成：

> We still have a benchmark that passes evidence-readiness gates, but our latest real-backend rerun does not support a learned-policy superiority claim. Moreover, the intended guardrail intervention did not visibly activate in the live traces, so the next blocker is instrumentation/runtime integration rather than another round of policy interpretation.

## 8. 下一步最优先，不要再发散

现在最值得做的不是继续扩 query，也不是继续写 policy 故事，而是先解决一个更基础的问题：

1. 查清 `ResearcherAgent` 中 policy advice / guardrail metadata 的记录链路
   - 为什么 live rerun 里 `avg_policy_advice_count = 0`
   - 为什么 `avg_guardrail_trigger_count = 0`
   - 是未触发，还是触发了但没写入 `metadata_summary`

2. 做一个最小可控单题验证
   - 人为构造一个会触发
     - `no_search_yet_force_search`
     - `seeded_query_force_browser_before_stop`
     - `repetitive_search_force_stop`
   - 确认 live run 产出的 JSON 里真的能看到这些计数

3. 只有确认 guardrails 真正在 runtime 中生效并可观测后，
   - 才值得再跑一次 8-query cross-fold live

在这之前，再继续解读 learned vs heuristic 数字意义不大，因为当前连“干预是否真的发生”都还没被实验日志证明。
