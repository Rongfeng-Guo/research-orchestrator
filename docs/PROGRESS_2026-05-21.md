# DeepResearch Agent 继续推进记录

日期：2026-05-21

本轮目标不是再堆一个新 idea，而是继续把当前这条最像论文的主线往前推：

> 让 real-evidence agent 在缺少强搜索 API 的情况下，仍然尽量先命中用户 query 里已经明确给出的官方来源。

这一步的意义很直接：

- 不是为了伪造“搜索变强了”；
- 而是为了把“显式官方来源提示”真正落进工具层；
- 让我们能够更诚实地区分：
  - 搜索后端本身的能力；
  - query 中先验官方来源带来的帮助；
  - citation 后处理的作用边界。

## 1. 新增显式 URL seeded retrieval

更新：

- `src/tools/web_search.py`
- `tests/test_web_search_duckduckgo.py`

这次给 `WebSearchTool` 补了一层非常克制的能力：

1. 如果 query 本身包含显式 `https://...` URL，就先把这些 URL 抽出来；
2. 尝试轻量抓取这些页面；
3. 能解析 HTML 的，就提取 `title` / `description` / 首段文本；
4. 遇到 PDF 或其他非 HTML 内容，也保留成一个最小可用的 seeded source；
5. 再把这些 seeded source 插到搜索结果前面，并按 URL 去重。

这样做之后，工具层终于能理解下面这种 research-style prompt：

```text
Prefer these primary sources first:
https://...
https://...
https://...
```

而不是把这段文字当成普通噪声，仍然去 Bing HTML 随机搜一圈。

## 2. 为什么这一步值得做

当前瓶颈已经很明确：

- citation rendering 不差；
- real source inventory gate 已经能挡掉 mock；
- paper readiness 的主要阻塞，是 `source_relevance_low`。

也就是说，现在最需要修的不是“怎么再多出几个 URL”，而是：

> 怎样让 agent 更稳定地先接近真正相关、真正官方、真正可溯源的来源。

在没有新的 SerpAPI / Bing API / Bocha / Metaso key 之前，显式 URL seeded retrieval 是当前成本最低、实验卫生最好的推进方式。

它不会让我们误以为已经拿到了强搜索能力，但会让以下实验更干净：

- query 已经给出官方入口时，agent 是否会优先使用；
- seeded source 能否提升 source relevance；
- 结果提升到底来自工具层处理，还是来自搜索后端本身。

## 10. 关键根因：primary-source hint 在 agent 层丢了

跑完 seeded fast probe 后，真正暴露出来的不是搜索后端 bug，而是链路 bug：

- 原始 query 里明明带了显式官方 URL；
- 但 `ResearcherAgent` 调 `web_search` 时，模型把 query 压缩成了普通关键词；
- 因此 `WebSearchTool` 根本收不到这些 URL，seeded retrieval 在完整 agent loop 里并没有真正生效。

这解释了为什么：

- 直接手工调用 `web_search` 时，官方源能顶到第一位；
- 但完整 cache 里的 source 列表，仍然经常是泛化网页和二手来源。

## 11. agent 层修复：把官方 URL 自动补回 tool query

更新：

- `src/agents/researcher.py`
- `tests/test_search_policy.py`

现在 `ResearcherAgent` 会：

1. 从 `task.description` / 原始 `context["query"]` / `task.search_hints` 里提取显式 URL；
2. 若模型发出的 `web_search` query 没带 URL，就自动把这些 primary URLs 拼回去；
3. 同时把：
   - `query_text` 记录成真正执行的 augmented query；
   - `original_query_text` 记录成模型原始压缩 query。

这使得我们终于能分清：

- 模型原本想搜什么；
- 最终喂给搜索工具的是什么；
- seeded retrieval 是否真的在完整 agent loop 中生效。

## 19. browser `br` 解码修复：GitHub 官方博客不再把样本打穿

继续往下查 `fast_ai_code_001` 的失败根因后，问题最终收敛到了 `BrowserTool`：

- `src/tools/browser.py`
- `tests/test_browser_tool.py`

   - `Accept-Encoding: gzip, deflate`
2. 若仍遇到 payload 解码异常，则自动退回原始字节抓取，再按：
   - `gzip`
   - `deflate`
   - `br`
   手动解压

并新增了压缩 payload 解码回归测试，确保这不是一次性热修。

真实 live probe 里，先前会失败的 GitHub 官方研究博客现在已经能稳定读回正文片段。

## 20. planner 稳定性修复：长 URL query 不再在规划阶段白白失败

- `src/planner/planner.py`

3. 更关键地，若规划输出仍不可解析，则自动退回一个确定性的单 `search` 任务：

这一步非常值，因为它修的不是单个样本，而是整条低预算 real-evidence fast pipeline 的吞吐稳定性。

## 30. 针对 fold variance 的第一轮工程修正：在 agent 接入层补 search-policy guardrails

在读完 4-fold live 结果后，当前最高杠杆的问题已经不是“再跑一轮同样的实验”，而是先收紧两个会污染结论的行为失真：

1. **premature stop**
   - 典型表现：还没真正检索或还没打开 primary source 原文就停下
2. **repetitive continue**
   - 典型表现：已经有 browser 证据，但继续做高度重复的 search/browser 循环

这两个问题如果不先压住，再继续扩 heldout，只会把方差继续带大。

因此这轮我没有改训练器或 reward，而是先在 `ResearcherAgent` 的 policy 接入层补了一层保守护栏：

- `src/agents/researcher.py`
- `tests/test_search_policy.py`

新增的 guardrails 只有三条，而且都是围绕当前 benchmark 的已知错误模式：

1. **zero-search guard**
   - 若 agent 还没有任何 search/browser 行为，就算 learned 想停，也必须先做一次检索
2. **seeded-browser-before-stop guard**
   - 若 query 自带显式 primary URLs，且已经搜到候选页面但还没打开任何原文，则不允许直接停，必须先走一次 `browser`
3. **repetitive-search-stop guard**
   - 若已经发生 `search + browser`，且后续 query overlap 很高或 budget 已明显上升，则强制停下总结，避免无意义重复

为了保持现有 runtime prompt 兼容性，这些 guardrail guidance 仍沿用：

- `[SEARCH POLICY]`

前缀，这样不会破坏现有的 policy-guidance 注入流程。

## 31. 这轮不是新指标，而是把下一轮 live 实验做干净

这轮的验证重点是：

- 新 guardrails 是否按预期触发
- 旧的 search-policy guidance 流程是否仍能正常工作
- 是否破坏现有 benchmark / split / head2head 工具链

新增并通过的单测覆盖了：

- zero-search 时强制 search
- seeded query 在 stop 前强制 browser
- 高重叠继续搜索时强制 stop

全量测试现在是：

- `106 passed in 7.77s`

所以这一轮虽然没有新增 live headline 数字，但它把下一轮 live rerun 的目标收缩得更明确了：

- 先看 fold 01 的 premature-stop 是否被压住
- 再看 fold 02 的 over-search 是否被压住
- 如果这两类错误下降，cross-fold variance 才有机会真正收敛
